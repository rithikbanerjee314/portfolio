# Personal Portfolio — Project Reference

Portfolio site for Rithik Banerjee (Columbia CS/Physics junior), built for job applications. This doc reflects the **current state** of the project as of 2026-07-25 (v4.1). It was rewritten from a long chronological changelog into a current-state reference — see git history / prior conversation for the blow-by-blow if ever needed; what matters going forward is what's true *now* and the lessons below that prevent re-introducing fixed bugs.

**Stack**: Next.js 14 (App Router) + TypeScript + Tailwind + React Three Fiber 8 / drei 9 / three.js **0.169 (pinned — do not bump without upgrading drei/fiber/rapier in lockstep)** + `@react-three/rapier` (physics) + Framer Motion + zustand. Hosted on Vercel free tier, deployed 2026-08-03 at `https://rithikbanerjee.com` (custom domain, purchased and attached through Vercel's own domain dashboard — no separate registrar involved; Vercel project name `portfolio` under the `rithikbanerjee314s-projects` team).

## The big picture

The site is **one persistent, full-viewport R3F `<Canvas>`** (`components/world/WorldCanvas.tsx`) — not a scrolling DOM page with a hero canvas. The visitor scrolls through drei's `ScrollControls` virtual scroll region, which drives a camera rigged to a `CatmullRomCurve3` "mountain climb" path. Content (projects/hobbies) lives at **stations** along that path, each with a real interactive 3D object standing in for a project or hobby, plus a DOM side panel with the actual write-up.

This was a full rebuild of an earlier "static card grid + modal" version, which the user rejected outright as too generic. Since then it's been through ~7 rounds of user testing feedback, each round fixing real bugs (not just taste calls) — see **Lessons learned** below before touching camera/terrain/physics code, several of these are non-obvious and easy to reintroduce.

## File map

- `components/world/stations-meta.ts` — pure station data, **zero dependency on "three"**: `StationDef`, `STATION_ORDER` (base → intro → chess → soccer → tokamak → piano → vault → summit, each with a `t` position 0–1, a lateral `side`/`distance` offset, and — since 2026-08-02 — a `short` one-to-two-word label used ONLY by the header nav; the full `title` still drives every pane heading and `StationPane`'s reopen tab, kept as two fields so they can't drift. Current shorts: About / Chess / Automation / Fusion / Music / Projects / Summit — "Summit" rather than "Contact" because the header already has a Contact button beside it that does something different (opens the pane in place, no travel) — the trail map used to have its own entry between intro and chess, merged into intro's own sign 2026-07-27, see the `IntroStation.tsx` bullet below), `nearestStation()`, `STATION_ARRIVAL_EPSILON`. Split out of `path.ts` on 2026-07-27 — see lesson 35 — specifically so DOM-only code that's part of the page's always-eager tree (`Overlay.tsx`, `StationPane.tsx`, `lib/hooks.ts`) can get station metadata without transitively pulling all of `three` into the first-load bundle. **Anything that needs just the list of stations/order/progress, not real 3D geometry, imports from here, not from `path.ts`.**
- `components/world/path.ts` — the climb path's actual 3D geometry, needs `three`: `PATH_CURVE` (a `CatmullRomCurve3`), `getStationAnchor()`, `getCameraPoint()`/`getLookAheadPoint()`. Re-exports everything from `stations-meta.ts` too (so existing `import { STATION_ORDER, getStationAnchor } from "./path"` call sites elsewhere in the 3D-only tree keep working unchanged) — but never import *this* file from eager/DOM-only code, only from things already behind the `WorldCanvas` dynamic boundary. The `fish` station was renamed `vault` (2026-07-25) when the fish object moved off the main stage into the vault room — same `t`/`side`/`distance` slot, just a different object and a different click behavior standing there now.
- `components/world/CameraRig.tsx` — drives camera position/orientation from `useScroll().offset` every frame. No forced/magnetic snapping — scroll position changes **only** from real user scroll or the explicit `requestScrollTo` handler (nav clicks, station labels, hash deep-links); the visitor can stop anywhere. **Click-to-travel is an eased tween, not a jump** (2026-08-01): `requestScrollTo` used to assign `el.scrollTop` in one statement, leaving ScrollControls' fixed ~0.3s damping as the only thing between the visitor and the destination — so crossing the entire mountain took about as long as hopping one checkpoint, and both read as a snap. It now animates `scrollTop` over `TRAVEL_MIN_MS + TRAVEL_PER_PROGRESS_MS * distance` (1.1s–5.3s) using **smootherstep** (quintic: zero first AND second derivative at both ends — the cubic smoothstep's non-zero acceleration at the endpoints was itself a visible jolt, since the camera position is separately lerped toward this value every frame). Any real scroll input (`wheel`/`touchstart` on the scroll element) cancels the tween immediately, otherwise a mid-travel wheel nudge would be silently overwritten on the next frame and the page would feel stuck. `requestScrollTo(t, { immediate: true })` skips the animation; used for hash deep-links, and taken automatically for `prefers-reduced-motion` and for travel shorter than `TRAVEL_NEGLIGIBLE`. **`TrailMapGate`/`VaultGate`'s `PENDING_TIMEOUT_MS` had to go 3000 → 8000 to match** — at 3s that fallback could fire while the camera was still legitimately in transit. The frame loop is also allocation-free (module-scope scratch vectors + `sampleTerrainInto` + `getCameraPointInto`/`getLookAheadPointInto`), and writes its three store fields through the single batched `setCameraState` rather than three separate setters that each triggered their own synchronous re-render of the whole DOM overlay. **Zoom and look-around are currently INERT — see lesson 47**: both are wired to listeners on `gl.domElement`, which ScrollControls' scroll `<div>` covers entirely, so they never fire. Everything described in the rest of this bullet about them is the code's *intent*, not observed behaviour. Zoom is ctrl+wheel/pinch (kept off the plain scroll wheel, which drives path progress). Look-around is bounded pointer-drag, live only while "parked" (`isParked`, low scroll velocity + close to a station's `t`), applied as a true rotation of the camera→target direction (yaw around world-up, then pitch around the yawed right axis) — not a fixed-unit lateral shift of the target point, which would sweep a shrinking angle the farther the target is from the camera (see lessons). The yaw/pitch clamp itself also widens from the tight ground-level bound toward a much wider one as `vistaWeight` (see below) ramps in, so the summit overlook is actually pannable across its full width, not just the tight per-station range. Near a station, the look target blends from "down the trail" onto that station's object (objects are the subject, path is context) — **except summit**, which is deliberately excluded from that blend (see lessons). Past `t>0.88`, both camera **position and target** blend into a dedicated summit overlook (~9 units above the peak, 5 units to the side of the flag, looking toward `t≈0.35` near ground level) — high enough to lay out every checkpoint below, angled enough to keep the horizon visible, with the flag still in frame; look-around stays live through this blend so every station's `StationLabel` can be panned to and clicked from up there, same as ground level. The camera's final position (`dollied`, after zoom-dolly and vista lerp) is re-clamped every frame against `terrain-utils.ts`'s `sampleTerrain()` height at its own `(x,z)` plus `CAMERA_GROUND_CLEARANCE` (1.4 units) — a straight-line lerp between the on-path position and the overlook point doesn't know the mountain's actual rising shape in between, so partway through the blend it could dip below the surface even though both endpoints sit above ground (the "clips through the mountain" bug fixed 2026-07-26). Clamping the real height at each frame's actual `(x,z)`, rather than trusting the hand-placed endpoints, fixes this without changing the final overlook position itself.
- `components/world/terrain-utils.ts` — shared terrain-shaping math: `sampleTerrain(x,z)` returns height/trailDist/onPad/**padWeight** for any point, used by `Terrain.tsx`, `PathRibbon.tsx`, and `Vegetation.tsx`; `sampleTerrainInto(x,z,out)` is the same thing without the allocation, for the two hot call sites (the per-vertex terrain build loop and `CameraRig`'s per-frame ground clamp). `nearestPathInfo()` does proper point-to-**segment** projection with linearly-interpolated height (not nearest-sample-point — see lessons), accelerated by **chunked AABB pruning** (2026-08-01): path segments are grouped 8 at a time with an XZ bounding box each, and a chunk whose box is already farther than the best distance so far is skipped wholesale. This is a lower-bound test, so it's exact — verified bit-identical to the old unpruned scan across 160,801 probe points covering the entire terrain footprint (0 mismatches, max |Δ| = 0), while visiting ~13 segments per call instead of all 240 (~3.3x faster wall-clock). Worth having because this function is called ~80,000 times synchronously while the world builds AND once per frame forever after. Station pad flattening picks the **single strongest/closest pad** by weight, never sequentially compounds multiple pads (see lessons).
- `components/world/Terrain.tsx` — one continuous vertex-colored `PlaneGeometry` (not tiled), **smooth shaded** (not flat — smooth shading is what makes it read as continuous rolling ground rather than faceted panels), grass/dirt/rock/snow by altitude+slope, per-station biome tinting (nearest-only, not compounded), edge skirt folds the boundary down so there's no floating-plane rim at grazing angles. The vertex-color pass was rewritten 2026-08-01 to fix reported "splotchy" terrain and weak separation between terrain types — see lesson 40, which is the thing to read before touching this loop again. In short: colors are now built as **ordered weighted layers** (grass base + biome tint → rock by slope → snow by altitude → dirt by trail distance → pad stone), each blended in over a deliberately NARROW `smoothBand()` transition rather than selected by a hard `if/else` threshold, and all per-vertex randomness is gone — variation comes from `macroVariation(x,z)`, a smooth long-wavelength function of world position. Band edges live in named constants at the top of the file (`ROCK_NY_FULL`/`ROCK_NY_NONE`, `SNOW_START_BELOW_SUMMIT`/`SNOW_BAND`/`SNOW_LINE_WANDER`, `DIRT_CORE`/`DIRT_BLEND`, `PAD_FULL`/`PAD_NONE`) — widen a band to soften a boundary, narrow it to sharpen one; that's the only knob needed. Note `smoothBand(edge0, edge1, x)` takes GLSL's argument order, deliberately NOT named `smoothstep` because `THREE.MathUtils.smoothstep` takes `(x, min, max)` and is used elsewhere in this codebase.
- `components/world/PathRibbon.tsx`, `Vegetation.tsx`, `Clouds.tsx`, `Beacons.tsx`, `Waterfall.tsx`, `SkyEnvironment.tsx`, `WindParticles.tsx` — environment dressing. `Waterfall.tsx` was rebuilt 2026-08-02 — **site chosen by measurement, not by eye.** A sweep of 597 candidate points tested, for every camera position along the climb, whether the point is inside the frustum AND has clear line of sight (terrain sampled along the ray, so ridges occlude). The old site beside tokamak scored **9% of the climb visible, weighted presence 2.6** — effectively invisible — and had a real bug: the curtain hung straight down from the cliff top while the plunge pool sat 12 units away horizontally, so the water landed nowhere near it. The new site (lip at `13.5, -3.5`, ~9-unit drop down the local fall line) is **visible 31% of the climb and in frame from t=0.00 to t=1.00** — landing page, whole ascent, and the summit overlook looking back — weighted presence 28.4, ~11x the old. It sits 9.9 units beyond the tokamak anchor so it backdrops the research station without competing.

  **Geometry rebuilt twice more the same day** after user feedback, first from description then from a real screenshot. Round one: the falls read as "a completely new random giant block of rock" glued onto the mountain with a discontinuous ending. Root cause: the original cliff was a flat-bottomed box (plus a scatter of dodecahedrons) placed at one fixed height near the pool — since the real ground there is sloped and noisy, a shape with a single flat base can only ever match the terrain at one point; everywhere else it necessarily floats above or clips into it, which is exactly what read as "random block." Fixed by sampling the real terrain (`sampleTerrain`, the same function the ground mesh itself is built from) at points along the actual fall line, and building the water sheet as a **terrain-hugging ribbon** that follows that sampled profile instead of a flat plane hanging in open air — the falls now runs the real ~9-unit horizontal distance rather than a compressed fake cliff near the pool. Flanking rock banks are each **individually grounded at their own sampled position** (not interpolated from the centerline), so nothing floats or clips regardless of how the slope wobbles underneath.

  **Round two**, from an actual browser screenshot, surfaced two things the position-only math from round one couldn't have caught: rock banks visibly sitting INSIDE the fanned-out water near the base, and a hard rectangular cutoff with no pool — "the water is literally just stopping at an arbitrary point." Root cause of the first: the sheet's width-vs-distance shape lived only in the vertex shader (`pos.x *= 1.0 + fall * 0.42`), a GPU-side transform the CPU-side bank-placement code had no knowledge of, so banks cleared a narrower estimate of the flow than what the shader actually rendered — worst where the shader's own widening was largest, i.e. near the base. Root cause of the second: a flat, level `circleGeometry` pool sitting on genuinely sloped, unflattened terrain — a level disc and a sloped surface can only ever coincide at one point, so the disc necessarily buried its uphill half and floated its downhill half, and at this camera angle read as nothing at all.

  Fixed by making width-vs-distance a single CPU-side function, **`halfWidthAt(dist)`** (narrow at the lip → bulges to `POOL_BULGE=1.55x` at the reference "pool" point → tapers to `TAIL_TAPER=0.4x` by the end of a `TAIL_RUN=3.4`-unit fading tail past it) — used for BOTH the ribbon geometry AND the bank clearance, so the two can never disagree about how wide the water actually is at a given point. The vertex shader keeps only a small residual ripple (`fall * 0.02`, down from `0.42`) for fine turbulence, deliberately kept small enough to never eat into the CPU-computed clearance margin (verified explicitly, see below). Rather than a level pool fighting a sloped surface, the flow now **continues past the reference point as a narrowing, fading tail** — `SHEET_FRAGMENT`'s alpha is multiplied by `smoothstep(uTailFadeStart, 0.0, vUv.y)`, full through the reference point and dissolving to nothing by the tail's real end — so it reads as "keeps flowing down the mountain out of view" rather than a hard boundary. The old flat pool disc and its separate rim-rock ring are gone entirely; the unified bank-rock loop now runs the banks' whole length including the tail, each still individually grounded on real sampled terrain.

  Measured against the real terrain and the actual per-rock footprint (`scratchpad/waterfall-audit.mjs`, replaying `terrain-utils.ts`'s actual `sampleTerrain` — rebuild it the same way as `terrain-audit.mjs` if gone, by copying `terrain-utils.ts`/`path.ts`/`stations-meta.ts` into a throwaway folder with explicit `.ts` import extensions so plain `node` can resolve them): the profile is **strictly monotonically descending** over the full run+tail (0 upstep violations), and — the actual bug from the screenshot — **every bank rock's visual footprint (radius included) clears the water's true rendered edge, INCLUDING the vertex shader's residual widening, by at least 0.26 units** (checked at high-tier density, the worst case; first measured at -0.064, i.e. a real overlap, before the margin/ripple-coefficient constants were tightened — don't loosen `SHEET_VERTEX`'s ripple coefficient or the banks' base margin without re-running this check). This is still geometry/position math only, not a lit-pixel check — per lessons 27/28, still needs the user's own eyes in a real browser to confirm it actually looks right, since this environment cannot render the canvas tree at all (see dev-environment quirks) — but the specific two bugs reported from the real screenshot are the ones this pass targeted, and both are now numerically verified fixed rather than just no-longer-visually-obviously-wrong. **The water's realism comes from one idea**: a parcel that left the lip is at depth d = ½gt², so its age is t ∝ √d — driving the streak phase off `age` rather than off depth makes streaks automatically short and dense at the lip and long and stretched near the pool, which is the strongest cue that it's falling rather than a scrolling texture. Everything else follows (coherent glassy sheet up top → filament break-up as it accelerates → horizontal spread → thinning at speed → whitewater at impact). Spray droplets follow **real ballistic arcs** evaluated in the vertex shader (`position + vel*t + ½gt²`), recycled per-particle. **Verify shader edits by compiling them in a real WebGL context** (all four vertex/fragment pairs were compiled and linked this way) — `npm run build` type-checks TypeScript and cannot see GLSL errors at all. `Beacons.tsx` renders **no visual pillar** — the glowing light-pillar mesh it used to draw at every checkpoint was removed 2026-07-26 at the user's request ("they look awkwardly placed"); the component now exists purely to compute label positions. Past `progress > 0.86` (the summit overlook), it computes a manual world→screen projection (`Vector3.project(camera)`, throttled ~20hz) for a point above each checkpoint and writes `{x, y, visible}` per station into `useUIStore`'s `beaconLabels`; `Overlay.tsx` reads that to draw plain DOM "click to travel" buttons, all a single uniform blue (`palette.ts`'s `ACCENT_SIGNAL`, not per-station accent — also per user request, so the summit-overlook labels read as one consistent set rather than a mix of each station's own color). Deliberately **not** drei's `<Html>` (see lessons 26–28: that mechanism was tried first here and was invisible specifically from this same overlook camera, for reasons never root-caused even after reproducing it fresh) — reimplementing the projection ourselves avoids depending on whatever's broken in that path. **Still needs live verification from an actual browser** — this dev environment's Browser pane has a frozen `requestAnimationFrame` loop (confirmed directly: a raw rAF loop never ticks here), so `useFrame` never runs and neither this nor any earlier version of this projection could be visually or DOM-verified from here. Waterfall's whole profile (lip through the fading tail) calls `sampleTerrain()` directly so it sits on real ground, not hand-picked offsets.

    Geometry is a barrel-top dome lid (not a flat box), matching a real treasure-chest silhouette, with its **flat end-caps facing the chest's left/right sides** and its curve running front-to-back (not the other way — this was wrong in an earlier pass and had to be corrected). `makeDomeGeometry()`'s approach, and *why* it isn't simpler, is worth reading before touching this again: building a half-`CylinderGeometry` directly with a shallow `thetaLength` (to get a gentle arc instead of a full towering semicircle) produces a **broken shape** — `CylinderGeometry`'s end caps always fan out from the central axis point, so any partial-angle slice gets pie-slice caps that dip down to the axis center instead of a flat chord. That's invisible in the special case of an exact half-circle (`thetaLength:π`, where the axis center happens to coincide with the chord already) but very visible otherwise. The fix: build the *proven-correct* full semicircle first (`thetaStart:-π/2, thetaLength:π` then `.rotateX(-π/2)` — flush at y=0, peak at y=radius, clean caps, verified via the bounding-box-against-real-`three` Node-script technique from lesson 27), **then non-uniformly scale Y** to whatever peak height (`sagitta`) is wanted — scaling can't break a cap's flatness, it only changes how tall the dome reads — and only *then* `rotateY(90°)` to swap which axis is the curve's chord and which is the flat-ended extrusion axis. Currently `sagitta == chordRadius` (the scale is a no-op) — the user asked for the full half-cylinder back after briefly trying a shallower arc, so the constant is set to equal the radius rather than special-casing the scale step away, keeping "make it shallower again" a one-constant change. Every step of this chain was checked against the real installed `three` package's actual bounding boxes in a throwaway Node script before use, not just derived on paper — this dev environment can't render WebGL to check visually, and the on-paper derivation for the compound rotate+scale+rotate case was actually wrong on the first attempt (assumed a shallow-arc slice alone would sit flush at y=0; empirically it didn't, for the pie-slice-cap reason above). Multi-material arrays (three.js's per-face geometry groups — `BoxGeometry`'s 6 face groups, `CylinderGeometry`'s 3 groups when `openEnded:false`) give the base/dome two-tone wood coloring (lighter front/back and dome curve, darker sides and dome end-caps — the end-caps' dark tone reads correctly on the *sides*, where they belong) plus dark corner/seam trim bands, 5 arch bands spread across the *width* (matching the reference image — they wrap the curve, so once the curve's orientation flipped, the bands' spread axis had to flip with it, from depth-spread to width-spread) — 3 in the middle (`archGeo`, `openEnded:true`, nothing borders their ends) plus 2 "edge rails" (`edgeRailGeo`, real caps so they read as solid/flush rather than hollow) sitting almost flush against the dome's own left/right extremes, nudged proud by `EDGE_RAIL_MARGIN` (0.006 units, imperceptible) so their caps aren't exactly coplanar with the main dome's own. The edge rails additionally use their own `edgeRailMaterials` array — lateral surface `TRIM_DARK`, both caps `WOOD_SIDE` — so only the actual thin wrapped band reads as black trim; without this the cap (a full disc, not a ring) painted almost the entire visible side of the chest black. See lesson 31 for the full three-pass story of getting this one decorative detail right — a diamond escutcheon + smaller hasp (a box rotated 45° in-plane reads as a diamond) + rivets — on the **back** face (`-halfD`, opposite the hinge; moved there from the front at the user's explicit request), side handles (`TorusGeometry`, hole-axis rotated per lesson 23's convention), corner feet, and a thin border (`SIDE_FRAME_THICKNESS`/`SIDE_FRAME_PROUD`) tracing the base's bottom/front/back edges on each side face — added at the user's request "for continuity" with the dome's edge rail above; the top edge doesn't need its own bar since the existing horizontal seam band already covers it, closing the outline into one continuous frame around each side. That side-frame border only covers the base's straight-edged rectangle, though — the dome's own curved rim (the semicircular boundary of its flat side cap, as seen looking straight at the chest from the side) still needed its own trace, since the width-spanning arch/edge-rail bands read as bands wrapping the curve from front/angled views but don't themselves outline this side-on silhouette. That's `rimStripGeo`, parented inside the same lid pivot group as the dome (so it opens with the lid) — its two ends meet the side-frame border's front/back bars right at the seam, closing the full outline around each side. **First attempt used a flat `THREE.RingGeometry` semicircle** (`thetaStart:0, thetaLength:π` then `.rotateY(π/2)`) sized to the dome's exact Y:[0,radius]/Z:[-radius,radius] footprint — correct in *position*, but the user reported a gap between it and the side-frame border from certain angles, because a flat 2D ring has **zero thickness** along the chest's X axis: viewed close to face-on it reads as a normal-width line, but from any other angle its apparent width shrinks toward nothing (a flat plane foreshortens to a hairline when viewed edge-on), while the side-frame border's actual 3D boxes keep their real thickness from every angle — the two stopped visually lining up as soon as the camera moved off that one flattering angle. Fixed by rebuilding it as a genuine `THREE.TorusGeometry` half-tube (`radius:DOME_CHORD_R, tube:RIM_TUBE_RADIUS, arc:π`, then the same `.rotateY(π/2)` since a torus's default hole axis is Z — lesson 23) — real volume in every direction, so its apparent width stays consistent regardless of viewing angle, matching the side-frame border's own behavior. Even after that, its position was computed to be exactly tangent to its two neighbors (the outer edge rail and the side-frame border's front/back bars) — zero overlap margin — which still read as a gap; `RIM_TUBE_OVERLAP`/`SIDE_FRAME_TOP_OVERLAP` (both 0.02 units, see lesson 32's continuation) push each piece to genuinely overlap its neighbor instead of just meeting it. General takeaway: a flat plane and a real 3D volume are not interchangeable for "does this look like it connects to that other 3D piece from any angle" — they only agree at the one viewing angle where the flat plane happens to face the camera — and even two real volumes positioned exactly tangent can still read as a gap; deliberate overlap, not exact meeting, is what actually reads as "one connected piece."

## Initial load performance & transitions (as of 2026-07-27)

Before this pass, the initial page load took roughly 30s locally and the 3D world just popped into view instantly whenever it happened to finish, with no designed hand-off; the vault and trail map had the same "instant pop" problem on open. This went through two rounds: an initial fix for raw load time (points 1–4), then a follow-up round (points 5–7) after real-browser testing surfaced that the deferred-loading approach from round one had itself introduced new hitches — "glitchy on first pass," camera panning glitches, and vault/trail-map transitions that still weren't fully smooth.

**Round one — load time:**

1. **`three.js` was being eagerly downloaded on every page load, despite living entirely behind `next/dynamic({ ssr: false })` boundaries.** Root cause: `path.ts` (needs `three` to build `PATH_CURVE`) was the only source of `STATION_ORDER`, and three files in the page's always-eager tree (`Overlay.tsx`, `StationPane.tsx`, `lib/hooks.ts`) imported `STATION_ORDER` from it just for plain station metadata — dragging all of `three` along for the ride. Confirmed directly against a *production* build's served HTML (`npm run build && npm run start`, then inspect `<script src>` tags — the `next build` summary's "First Load JS" number does NOT distinguish eager vs. dynamically-fetched chunks, so it stayed misleadingly unchanged while this was being fixed): a ~680KB `three.js` chunk was present as an unconditional `<script async>` tag. Fixed by splitting the pure data out into `stations-meta.ts` (zero `three` dependency) and repointing the three eager files at it — see lesson 35. This alone dropped the route's reported First Load JS from 310KB to 141KB.
2. **Even after that, packages shared across multiple `next/dynamic` boundaries (three/@react-three/@dimforge, used by `WorldCanvas`, `TrailMapCanvas`, and `VaultCanvas` alike) could still get hoisted by webpack's default `splitChunks` heuristics into a chunk that's eagerly `<script async>`-tagged.** Fixed with a dedicated `threeVendor` cache group in `next.config.mjs` scoped to `chunks: "async"` — see lesson 36. **This override crashes `next dev` outright if applied unconditionally**: dev mode sets `config.optimization.splitChunks` to the literal boolean `false`, not an object, so the override is guarded with `if (!isServer && config.optimization.splitChunks)`.
3. **`npm run dev` switched to Turbopack** (`next dev --turbo`) — cut cold-compile time roughly in half in local testing (~26s → ~9s for the first request in a fresh dev process). This is a one-time, per-dev-server-process cost with no equivalent in production (`next build` pre-compiles everything ahead of time) — further code-splitting was tested and found to have **no effect** on this number (see lesson 39), so don't chase it further via bundle restructuring.
4. **Reveal transition**: `app/page.tsx` wraps all DOM/canvas content in a `motion.div` that stays at `opacity:0` until `sceneReady && minTimeElapsed` (a 400ms floor purely to avoid a one-frame flash on an already-warm cache, not a target load time), crossfading in as `LoadingScreen.tsx`'s splash fades out.

**Round two — the deferred-loading approach from round one caused new hitches, fixed here:**

5. **`WorldCanvas.tsx`'s core scene (terrain/sky/camera/intro/summit — the minimum for "the mountain has loaded" to read as true) mounts immediately; everything else is staged across real animation-frame boundaries, not one synchronous burst.** `SceneReady` (a `useFrame`-based "first real frame painted" signal, not just "component mounted") used to fire the page reveal directly — see round three below for why that changed — and schedules the deferred tiers' mount via `requestAnimationFrame`: decorative dressing (`DeferredEnvironment.tsx` — vegetation/clouds/beacons/wind/waterfall) and physics + the five interactive stations (`DeferredStations.tsx`) both mount together one frame after the core's first frame. Both chunks are also prefetched (plain `import()`, fire-and-forget) the instant `WorldCanvas` mounts, in parallel with the core scene — decoupling "code is downloaded" from "code executes/mounts." The five interactive stations no longer stagger their OWN mounting on a timer (an earlier version of this file did, ~220ms apart) — that was actively counterproductive: a visitor scrolling quickly right after the reveal could reach a station before its staggered turn came up and watch it pop into view mid-scroll, with no real benefit left once point 1's fix removed the actual eager-bundle problem the stagger was compensating for. See lesson 37.
6. **`Vegetation.tsx`'s scatter-placement was the single largest synchronous cost in the whole deferred tier** — its rejection-sampling loop does up to `count * 14` candidate points per category (trees/grass/rocks), each costing a full `sampleTerrain()` call (an O(239) scan over the path) plus up to two more for the slope check; at "high" device tier this was on the order of tens of thousands of terrain samples in one `useMemo`, a genuine multi-hundred-ms block. Fixed two ways: (a) each category (rocks → trees → grass, cheapest first) now computes on its own staged animation frame via a local `stage` counter, identical technique to point 5 but internal to this one component since it's the dominant single cost; (b) grass instance counts trimmed (`{low:0, mid:500, high:1100}` → `{low:0, mid:320, high:700}`) since grass was by far the most expensive category and a real density cut was the most direct way to shrink it — the `scatter()`/`buildInstancedMesh()` algorithms themselves are byte-for-byte unchanged, so this only affects cost and grass density, not correctness. See lesson 38.
7. **The vault/trail-map chunk prefetch used `requestIdleCallback`, which may rarely or never fire on this page.** `WorldCanvas`'s Canvas runs a continuous `requestAnimationFrame` loop indefinitely (camera damping, wind sway, etc.), so the browser may never consider the page "idle" by the heuristic `requestIdleCallback` uses — in practice this meant the prefetch could still be pending when the visitor's first click happened, defeating its purpose. Fixed by switching to a plain, deterministic `setTimeout` (1.2s after `sceneReady`) in both `TrailMapGate.tsx` and `VaultGate.tsx`.

**Round three — round two's staging still let the page reveal before every tier had actually finished, which read as "glitchy"/unfinished right after the page appeared; and the loading indicators themselves were generic:**

8. **`sceneReady` (the flag that drives the page reveal in `app/page.tsx`) now requires the core scene AND `DeferredEnvironment` AND `DeferredStations` to each report real completion — not just the core's first frame.** Round two revealed the page as soon as the core scene painted and let the two deferred tiers mount/pop in afterward; that made the *reveal* fast but meant the visitor could see vegetation, clouds, the waterfall, or the five interactive stations still assembling themselves after the page was already visible and interactive — reported as "not everything is fully rendered when I load the page." `WorldCanvas.tsx` now tracks three independent booleans (`coreReady`/`environmentReady`/`stationsReady`) and only calls `setSceneReady(true)` once all three are true. `DeferredEnvironment.tsx` takes an `onReady` prop it passes straight to `Vegetation`'s new `onFullyBuilt` callback (fired once its 3-stage build actually reaches the last stage — see point 6 — since Vegetation is the one piece here with real multi-frame cost; Clouds/Beacons/WindParticles/Waterfall are cheap enough to not need their own gating). `DeferredStations.tsx` takes an `onReady` prop wired to a `SceneReady` placed inside its own tree (after `<Physics>`/`StationsLayer`), which relies on all five station chunks being prefetched *directly* (not just the `DeferredStations` barrel module — see `WorldCanvas.tsx`'s `prefetchAllStations`) before it ever mounts, so `next/dynamic` resolves each station from an already-warm module cache instead of still being mid-fetch when that first frame renders. ## Mobile / small-screen layout (2026-08-02, revised same day)

The desktop experience is required to stay byte-for-byte unchanged while adding a real small-screen layout — not just "it happens to still render." One shared breakpoint is used everywhere this distinction matters: **768px** (`lib/hooks.ts`'s `useIsSmallScreen`, matching the existing `smallScreen` threshold in `detectDeviceTier` and `WorldCanvas.tsx`'s FOV logic below). Every mobile-only CSS tweak in `Overlay.tsx`/`StationPane.tsx` uses Tailwind's `max-md:` variant (never edits to the base/unprefixed classes), and the one genuinely structural difference (the info panel) is a full separate React render branch, not a CSS trick — see below for why.

- **"Everything is zoomed in, I can't see the full picture" — camera FOV, not a DOM issue.** `fov` on a `THREE.PerspectiveCamera` is the VERTICAL field of view; at a narrow portrait aspect ratio the resulting HORIZONTAL fov shrinks a lot even though the camera's position/orientation never changed, so wide station objects read as tightly cropped. `WorldCanvas.tsx`'s `ResponsiveCameraFov` component (mounted once inside `<ScrollControls>`, alongside `CameraRig`) widens the vertical fov below 768px to keep the horizontal field roughly matching a normal desktop aspect, clamped to `MAX_MOBILE_VFOV_DEG` (100°) so it never turns into a fisheye. At 768px and above this is a no-op — `fov` stays exactly the `55` the `Canvas` starts with. Deliberately separate from `CameraRig.tsx` (per its own doc comment, the most fragile file here) — this only ever touches `camera.fov`, never position/orientation/target math.
- **The info panel is a full bottom sheet on small screens, not a shrunk copy of the desktop side panel.** First pass just resized the existing right-side panel for mobile — reported back as "still way too big... takes up the entire screen... I don't like this view at all." The actual ask was a different INTERACTION MODEL, not smaller text: on screens under 768px, `StationPane.tsx` renders a completely separate JSX branch (gated on `useIsSmallScreen()`, not a CSS breakpoint, since the two variants differ in animation axis and auto-open behavior, not just size) —
  - Slides up from the **bottom**, not in from the right (`initial={{ y: "100%" }}`, not `x`).
  - Fixed height `h-[65vh]` — roughly two-thirds of the screen, anchored to the bottom edge, rounded top corners, a small grab-handle bar. The mountain stays visible in the remaining third above it. Content scrolls WITHIN that fixed height (`overflow-y-auto` on an inner div) rather than the sheet growing to fit — "get the pertinent info from the summary, scroll for more."

The ONLY way it opens is an explicit tap on the **bottom tab** (renamed conceptually from "reopen tab" to "open tab" — on small screens it's the sole entry point, not just a way back in after closing). Same `showOpenTab` boolean drives both variants; only the visual placement/animation axis differs (bottom pill with an ▲ vs. the desktop's vertical right-edge tab).

  - Also gone at the same time: the SummitPane/nav-label copy changes from earlier the same day (contact section retitled "Contact Me", "Thanks for climbing with me!", em-dash sentence split) are unaffected by any of this — same content, now inside whichever container renders.

On small screens the hint now moves to `max-md:top-20` (just under the header) instead of the bottom edge, via the same additive-`max-md:`-variant technique as everything else here; desktop's `bottom-5` is untouched.
- **Object interactions (chess/tokamak) reported as "much more finicky"/"quite broken" on touch than mouse — round two, after the FOV/preventDefault/viewport fixes above didn't fully resolve it.** Two further, more structural fixes:
  1. **`lib/dragState.ts`** — a shared `{ activeObject: boolean }` flag, set by `ChessStation`'s and `TokamakStation`'s own drag `onDown` (cleared on their own pointerup/`finishDrag`), and checked by `CameraRig.tsx`'s own look-around/zoom `onPointerDown`/`onPointerMove` before arming ITS drag. The reasoning: `CameraRig`'s look-around drag listens for pointerdown directly on the canvas element, entirely independently of the R3F synthetic event system that dispatches to meshes — and R3F's `ThreeEvent.stopPropagation()` (confirmed by reading `@react-three/fiber`'s own source, `events-*.js`: "Hijack stopPropagation, which just sets a flag") only stops iteration to OTHER meshes hit by the same raycast, it never touches the real native event, so it cannot be relied on to stop a second, independent listener elsewhere from also reacting to the same physical gesture. If the camera's own drag were ever armed at the same time as an object drag, the result — camera panning while you're trying to move the piece — reads exactly as "the piece's drag is broken." A touch drag naturally covers more physical distance than a mouse drag aimed at the same small target (bigger hand movement, more incidental jitter), so this conflict, if it exists, would be far more noticeable on touch than mouse — which matches the reported pattern (works on desktop, broken on mobile) far better than a pure feel/sensitivity difference would. This fix is a pure guard addition (an early `return`) with no effect if the conflict theory turns out to be wrong, so it's safe either way.
  2. **`ChessStation.tsx`'s tap-vs-throw decision moved from world-space to screen-space distance.** The old `CLICK_DISTANCE` (0.08) compared the king's WORLD-space displacement to decide "was that a tap or a real drag" (below the threshold → rest in place, above → throw). But the FOV-widening fix earlier the same day makes the SAME on-screen finger movement sweep a LARGER world-space distance on narrow viewports (a wider FOV means the same pixel delta corresponds to a bigger angular/world change) — so on mobile, ordinary finger jitter during an intended tap crossed the old world-space threshold far more easily than the same jitter would from a mouse, misreading taps as throws. Replaced with `CLICK_DISTANCE_PX` (6), measured in actual CSS pixels of pointer movement (`dragStartClient`/`lastClient`, tracked from `e.clientX/clientY`) — this reflects what the input device physically did, independent of camera FOV/zoom/distance, so the same gesture now means the same thing on any screen size or device.
- **Object tap/hold on touch — round three (2026-08-02), and this one found the actual mechanism.** Reported as tap/hold "glitching", fighting the camera, and popping **literal error overlays** on screen. Rounds one and two guessed at feel constants and at a conflict with `CameraRig`'s look-around; both were wrong, because both assumed the canvas is what receives pointer input. It isn't — see **lesson 47**, which is the thing to read before touching any pointer handler in this project. Summary of what actually changed:
  - **`lib/dragState.ts` is now a real gesture arbiter**, not just a boolean. It owns document-level **capture-phase, non-passive** `touchstart`/`touchmove` blockers that `preventDefault()` only while an object gesture is live, plus `touch-action: none` on the ScrollControls element for the gesture's duration. That is what stops one finger from dragging the object AND scrolling the climb at the same time. `CameraRig` registers `scroll.el` with it (`registerScrollElement`).
  - **`lib/useObjectDrag.ts`** is the single pointer-gesture lifecycle every draggable station object uses (`ChessStation`, `TokamakStation`). It guarantees `onEnd` fires exactly once per `start` — including on `pointercancel`, a second finger landing, tab-hide, and unmount — and reports `{ cancelled, movedPx }`. `movedPx` (CSS pixels) is what the chess tap-vs-throw threshold reads; a cancelled gesture drops the piece in place rather than throwing it.
  - **Pointer capture is guarded** (`capturePointer`/`releasePointer`) and taken on the element the event was actually dispatched to, not the canvas.
  - `CameraRig`'s own (currently inert, see lesson 47) drag got the same `pointercancel` + guarded-release treatment, and its `onUserScrollIntent` now ignores a touch that an object already claimed, so tapping an object no longer abandons an in-flight travel.
  - Still needs the user's real-device testing: this sandbox cannot commit the `<Canvas>` child tree at all, so none of the touch behaviour is reachable from here (see quirks). What IS verified here: `tsc --noEmit` clean, production build clean, no eager three/rapier `<script src>` in the served HTML, and the header/panel geometry measured at 1280 and 375 on fresh loads.
  - **Not attempted beyond this, and why:** any FURTHER per-station drag-sensitivity retuning (tokamak's rotation-per-pixel scale, exact pixel thresholds) was deliberately left alone beyond the two structural fixes above. This dev environment cannot render or interact with the `<Canvas>` child tree at all (see "Development environment quirks" below) — confirmed AGAIN this round: `document.querySelector('canvas')` exists but has zero siblings and is stuck at 300×150, meaning `ScrollControls`' own overlay div never gets created here, so even the DOM-level question of which element actually receives a real user's touch could not be resolved empirically from this sandbox, only reasoned about from source. Tuning a feel-based constant further here would be unverifiable guessing, not a fix for a concretely identified bug (lesson 46's warning). Needs the user's real-device testing to confirm whether the two fixes above actually resolve the reported breakage, or whether it points at something else entirely.

## Robustness measures in place

- `#station-<id>` hash sync restores scroll progress on load/back-forward/deep-link.
- `prefers-reduced-motion` respected throughout (shader/particle motion slowed, idle spins reduced, role-cycler slowed).
- WebGL feature detection → full DOM fallback, no canvas mounted at all.
- Device-tier detection (cores/memory/viewport/pointer-coarse) scales terrain tessellation, particle counts, and gates `physicsEnabled` — on `low` tier, chess/soccer/piano/tokamak fall back to lightweight procedural equivalents (fish has no physics variant to fall back from anymore, since it's static either way).
- All interactive stations are always mounted at full detail, regardless of distance or camera angle (see lesson 33 — the old proximity-based placeholder swap was removed after it could be triggered by more than just distance).
- Body scroll fully owned by drei's `ScrollControls` virtual region; no competing native page scroll.

## Lessons learned (read before touching camera/terrain/physics code)

These are real bugs found across testing rounds, generalized so they don't get reintroduced:

1. **Never sequentially blend across a loop of overlapping "influence zones"** (station pads, biome colors, etc.) — compounding across overlaps produces unintended bulges/muddy colors wherever two zones are close together. Always pick the **single strongest/closest** influence instead.
2. **Nearest-DISCRETE-SAMPLE-point search on a curve has real discontinuities** where adjacent samples' values differ (e.g. height on a climbing path) — the Voronoi boundary between samples is a visible seam. Project onto the nearest **segment** instead, with values linearly interpolated along it.
3. **One `<Physics>` world total, not one per station.** Each `<Physics>` component spins up its own Rapier WASM instance; creating/tearing these down as stations lazy-mount/unmount was a real source of scroll jank. Similarly, prefer **one shared fixed `RigidBody` with several `CuboidCollider` children** over many separate small `RigidBody`s (e.g. containment walls, piano key anchors) — a collider is far cheaper to add to an existing body than a whole new body is to create.
4. **Mesh-bound `onPointerMove`/`onPointerOut` breaks dragging on any mesh with an empty/hollow area** (e.g. a torus's center hole) — the pointer leaving the mesh mid-drag fires `onPointerOut` and cancels it. Use **window-level** `pointermove`/`pointerup` listeners instead.
5. **THREE composes Euler rotations intrinsically in X→Y→Z order.** Putting a "yaw" value in the Z slot when the object was already tilted by an X rotation rotates it around its own *already-tilted* local Z axis, not the world-vertical axis — silently wrong alignment. Put yaw in whichever slot is applied immediately after the axis that's still world-vertical at that point in the composition.
6. **A camera "looking at an object" blend breaks down when the object has zero lateral offset from the camera's own path** (the summit anchor sits directly on the path centerline, unlike every other station) — blending toward it pitches the camera to look almost straight down at point-blank range. Exclude that case and give it dedicated framing.
7. **Any DOM element on the same screen edge as a panel that can open on top of it will become unclickable whenever that panel is open.** The station quick-nav lived on the right edge — the same edge the info panel slides in from and auto-opens on arrival — and was invisible-but-present underneath it. Moved to the left edge.
8. **Additive-blended "fade" effects need a true zero floor**, not a small minimum — even a 12%-opacity residual reads as a bright wash against dark backgrounds/text once additive blending is involved.
9. **When an Euler-angle fix doesn't actually hold up, stop composing Euler angles — build the rotation from explicit orthonormal basis vectors instead** (`new THREE.Matrix4().makeBasis(x,y,z)` → `Quaternion.setFromRotationMatrix`, or `Quaternion.setFromUnitVectors` for a single-axis alignment like a cylinder's length axis). The soccer goal's top net was "fixed" once already by moving yaw into the Y Euler slot and still came out misaligned — basis-vector quaternions sidestep the whole intrinsic-composition-order question.
10. **A dynamic RigidBody with a hull collider on a tall/narrow mesh can tip over on its very first landing** if the hull is a faceted approximation (e.g. a low-segment-count `LatheGeometry`) — even a small spawn drop is enough to catch an edge. If the object should always rest upright (chess king, bowling pin, etc.), lock pitch/roll with `enabledRotations={[false, true, false]}` rather than tuning drop height/restitution and hoping.
11. **Procedural equirectangular sphere textures (soccer ball, etc.) need row spacing that exceeds the shape's own footprint**, and should skip drawing near the texture's top/bottom edges — those rows map to the sphere's poles, where UV compression piles many texture columns into a small surface area and turns any near-touching shapes into a solid dark cap.
12. **Particles meant to "flow along" a path need that path's own progression variable to dominate the update**, not a secondary/orthogonal one. The tokamak's plasma particles advanced their poloidal (tube cross-section) angle 5–10x faster than their toroidal (around-the-ring) angle, so they read as spinning in place rather than flowing around the torus — inverted from the intended toroidal-dominant motion.
13. **`applyImpulse` magnitudes are meaningless without knowing the body's actual mass** — a Rapier-default-density sphere collider ends up far lighter than intuition suggests (a 0.35-radius ball is ~0.18 mass units), so impulses tuned "by feel" produce wildly larger velocity changes than expected. Set an explicit `mass` prop rather than tuning impulse constants against an implicit, easy-to-get-wrong density. Similarly, a velocity computed from raw cursor-movement-per-frame (chess king throw) is unbounded — clamp it before `setLinvel`.
14. **A kinematic body being dragged (no gravity/collision while held) can be walked anywhere the drag plane covers** — the drag target needs its own explicit distance clamp back onto the station pad, since nothing physical stops it otherwise.
15. **Containment should be layered, not single-point:** physical walls tall enough that a bounded throw/kick genuinely can't clear them, a ceiling collider as a backstop, *and* a tight respawn watchdog (small buffer past the wall radius, not several units) as the last resort — relying on any one alone (e.g. a generous "+3 units" watchdog buffer) lets an escaped object travel visibly into the mountainside before it resets.
16. **`applyImpulse` stacks onto a body's *existing* velocity — it doesn't set it.** Clicking the soccer ball repeatedly kept adding impulse on top of whatever velocity it already had, with no cap, so a burst of clicks could build up enough speed to tunnel straight through a thin wall collider within a single physics step (discrete collision detection only checks start/end-of-step positions). Fixed with two independent layers: clamp linear velocity to a max speed every frame (so tunneling-speed is structurally unreachable), and `ccd` (continuous collision detection) on any dynamic body a visitor can repeatedly kick/throw. Both matter — the speed clamp prevents the condition, `ccd` is the backstop if it's ever reached anyway (e.g. from a single very hard hit before the next frame's clamp runs).
17. **A `useRef` target for kinematic drag interpolation must be seeded with the body's own current position at drag-start, not left at its default/stale value** — the chess king's `target` ref defaulted to world origin and was only ever updated inside `onMove`, so a plain click (down+up with no mouse movement between, meaning `onMove` never fires) lerped the kinematic body 40%/frame toward world origin for however many frames the click lasted, reading as a teleport/disappear-reappear glitch. More generally: **kinematic bodies are never stopped by fixed colliders in Rapier** (no collision response, just contact events) — while a piece is in kinematic drag mode, physical walls/ceilings do nothing, so containment during a drag has to be enforced entirely in the drag-target math itself (clamp on every write to the target, ideally also on the interpolated position actually sent to `setNextKinematicTranslation`, not just the raw pointer position).
18. **A drag plane implemented as a finite mesh (`onPointerMove` on a `<mesh>`) breaks at shallow ray angles**, not just on hollow-center meshes (see lesson 4) — once the true intersection of the camera ray with the plane falls outside the mesh's bounds (cursor high on screen, or camera positioned well above the plane further up the mountain), R3F's hit-test simply stops firing the event, and the dragged object freezes while the cursor keeps moving. Fixed the same way as lesson 4: window-level `pointermove`/`pointerup` listeners plus a manual `THREE.Raycaster` intersected against a true infinite `THREE.Plane` — there's no mesh to miss. Any future drag-on-a-plane interaction in this codebase should use this pattern from the start rather than a mesh-bound listener.
19. **(RECURRED 2026-08-02 with a different symptom — the header bar is now `pointer-events-none` with `pointer-events-auto` on the controls themselves; keep it that way.)** The second failure was station labels being unclickable: `Overlay.tsx`'s header sits at **z-30** across the full width of the screen, while every in-world `StationLabel` is a drei `<Html>` capped at **z-25** by `zIndexRange={[25, 11]}` — so anything the header's invisible middle covers is unreachable even though it renders perfectly visibly underneath. It hit the Research Station first because that label is mounted higher than any other (`anchor.y + 3.6` vs 2.1–2.6 elsewhere), so from lower on the trail it lands right under the bar and its "click to travel" went completely dead — reported as "the hitbox is not where the label is at all". Verified fixed via `document.elementsFromPoint` at the header's midpoint: `<header>` no longer appears in the hit stack at all, while the Resume/Contact controls still do. **Two standing rules from this: new header chrome gets `pointer-events-auto` on the control, never on the bar; and any DOM overlay element that could overlap the 3D scene must be checked against the `<Html>` z-index ceiling of 25.** Original entry follows. **The DOM overlay (`Overlay.tsx`) header bar has `pointer-events-auto` across its FULL WIDTH** (a flex container with content only at the far left/right, empty space between) — any window-level pointer drag whose gesture didn't originate with `setPointerCapture` will get silently retargeted to that header the moment the cursor crosses into the top strip, and since the browser's default mousedown behavior wasn't suppressed, can trigger native text-selection highlighting on nearby DOM text as the drag continues. Any canvas-originated drag gesture needs all three together: `e.preventDefault()` on the initiating pointerdown (stops the browser from arming a selection drag at all), `gl.domElement.setPointerCapture(pointerId)` (pins all further events to the canvas regardless of what's visually underneath, released on drag end), and `document.body.style.userSelect = "none"` for the drag's duration as a defensive backstop. This fixed text-selection-while-dragging, but was NOT the cause of the larger freeze described in lesson 20 below — don't stop at this fix if the symptom is "whole upper half of screen is dead," that's a ray-math problem, not a DOM-overlay one.
20. **`Ray.intersectPlane` against a plane below/at the camera's own height returns `null` for the camera's entire upper field of view, not just an edge case** — if the camera looks generally downward at a drag plane (true here: the camera sits above the chess board and looks down at it), any ray aimed at the upper portion of the screen has a level-or-upward direction that mathematically never crosses that plane, no matter how large the plane is (an infinite `THREE.Plane` doesn't fix this — it was never a bounds problem, see lesson 18's diagnosis was itself incomplete). This froze the drag target across nearly the whole upper half of the screen. The fix isn't a better plane — it's not depending on a real intersection existing: when `intersectPlane` returns null, fall back to a point far out along the ray anyway (`ray.origin + ray.direction * largeT`) and let the existing pad-radius clamp rein it back in. The piece then slides smoothly toward "up and away" instead of freezing, for any camera angle.
21. **A 0-restitution body doesn't "stop safely" at a wall — it reads as tunneling** whenever anything (a thin collider, a seam between segments, an off-axis convex hull) lets it interpenetrate even slightly before the solver corrects it, since there's no visible bounce-back to make the contact legible; it just looks like it vanished. Gave the chess king and both stations' walls real restitution (~0.5) so a wall hit is an obvious, visible bounce, not a silent stop. Separately: **CCD's time-of-impact solver is least reliable for non-primitive shapes at the seam between two flat wall segments meeting at an angle** — the chess king's collider is an auto-generated convex hull from a Lathe profile with thin extremities (cross finial, neck), exactly the kind of shape that can find a gap a sphere wouldn't. Fixed by going from 8 wall segments to 24 (generous overlap, near-zero seam) and thickening each collider (0.12→0.35 chess, 0.15→0.35 soccer) — more margin, not just more segments, since even a dense ring of paper-thin walls is still thin.
22. **An equirectangular texture on a `THREE.SphereGeometry` has a real mathematical singularity at both poles — no texture-side fix can ever fully solve it.** Rows near the top/bottom of the texture get compressed onto a vanishingly small circumference on the sphere, so *any* shape drawn there distorts, no matter its size, position, or margin (three separate attempts — pole margin, single oversized pole pentagon, symmetric row centering — all ran into this same wall from different angles, because none of them addressed the actual cause). The real fix: stop using a UV sphere. `makeSpherifiedBoxGeometry` in `textures.ts` builds a **spherified cube** (a `BoxGeometry` with every vertex pushed out to a fixed radius) — its default per-face UVs are ordinary 0–1 squares with zero compression anywhere, so a ordinary tileable **square** texture (`makeSoccerBallTexture`, since rewritten from 256×128 equirect to a plain 256×256 tile) reads as uniform panels from every angle, including what would have been the poles. Any other sphere-textured object added later (if it needs a non-trivial repeating pattern, not just a flat color) should use this same pairing from the start rather than an equirect canvas on `sphereGeometry`. Physics-wise, the RigidBody's collider must be set explicitly (`<BallCollider>`), not inferred from the geometry via `colliders="ball"`, since the mesh is no longer a literal sphere.
23. **`THREE.TorusGeometry`'s default hole axis is Z (big ring in the XY-plane) — any other torus-shaped thing in the same scene needs to be built with that same convention in mind, or explicitly rotated to match.** The tokamak's glass torus mesh had no rotation at all, while `PlasmaParticles`' hand-rolled parametrization put its ring in the XZ-plane (hole axis Y) — the two were built independently against different implicit axes and ended up perpendicular to each other. Fixed by rotating the mesh `+90°` about X, which swaps its Y/Z the same way and, as a bonus, lines up its `u` parameter with the particles' `phi` exactly (`cos→x`, `sin→z` in both). The toroidal field coils had the same class of bug one level down: each coil is itself a small torus, and since a torus is rotationally symmetric about its own hole axis, the *only* thing that needs aligning per-coil is that axis — no extra roll term. Each coil's hole axis needs to point along the main ring's local tangent direction (`(-sin a, 0, cos a)` at ring-angle `a`), which a plain `rotation={[0, -a, 0]}` produces from the default Z axis; the previous version composed multiple Euler slots (`[Math.PI/2, 0, -angle + Math.PI/2]`) trying to hit this indirectly and landed near, but not on, the correct plane.
24. **A transparent shell that fully encloses its own contents needs `depthWrite={false}`, even at very low opacity.** Every tokamak plasma particle sits inside the glass torus by construction, so the shell's near (camera-facing) surface is — by definition — always closer to the camera than every particle behind it. At 18% opacity it still *looked* like it should let particles show through, but depth writing is binary: a surface that writes depth at all fully occludes anything farther along that ray, regardless of how transparent it visually is. The fix is the standard treatment for any glass/energy-shell effect: `depthWrite={false}` (so it can't occlude its own contents) with `depthTest` left on (so real scene geometry like terrain still hides the whole assembly correctly). A related-looking but wrong fix was tried first — `depthWrite={false}` on the (opaque) field coils instead — which happened to also unhide the particles, but for the wrong reason (the coils, once correctly oriented per lesson 23, actually have real gaps and weren't the main occluder) and at real risk: an *opaque* object skipping depth-write can get incorrectly overpainted by farther geometry drawn later in the same opaque pass, since nothing stops that later draw from winning the depth test against an unset buffer value. `depthWrite={false}` is safe on transparent objects; be much more careful applying it to opaque ones.
25. **A fixed-distance lateral shift is not a substitute for an angular rotation when the camera-to-target distance varies a lot across the scene.** `CameraRig`'s look-around (`yaw`/`pitch` from pointer-drag) used to shift the look-target point sideways by a flat `yaw * 6` / `pitch * 4` unit offset. That reads as normal panning up close at a station (target only ~1 unit from camera), but from the summit's overlook vista the target sits many units away — the same flat offset sweeps a much smaller *angle*, so look-around was nearly inert exactly where the comments said it needed to work (panning to find and click a checkpoint from above). The fix: rotate the actual camera→target *direction* by yaw (around world-up) then pitch (around the yawed right axis), and rebuild the target at the original distance along that rotated direction — this keeps the angular sweep identical regardless of how far the target is. Paired with widening the yaw/pitch *clamp* itself as `vistaWeight` ramps in (tight bounds tuned for standing next to an object are too narrow for panning across the whole mountain from the overlook) — both pieces were needed; rotating the shift alone would still have been clamped too tight to reach every station.
26. **A `<Html distanceFactor={n}>` billboard scales inversely with camera distance — a real, worth-fixing issue, but it turned out NOT to be the reason the summit's labels were invisible (see lesson 28).** `StationLabel`'s own doc comment says "always-readable," but `distanceFactor={9}` was tuned against ground-level camera-to-station distances (~3-5 units) and never revisited once the summit overlook was added (camera 50+ units out). This is still worth having fixed on its own merits — a UI billboard meant to always be legible shouldn't shrink with distance without a floor — but treat this as a plausible-and-partially-true lead, not a confirmed root cause, until independently verified. It was accepted here on Node-simulated NDC coordinates alone, which only proves screen *position*, not that the element actually paints.
27. **When the sandboxed Browser pane can't render a canvas-heavy R3F scene (documented dev-environment quirk above), replaying the same math in a standalone Node script against the project's actual installed `three` package is a useful *partial* verification path — it can rule things out, it cannot confirm the fix.** Copy the relevant pure functions (curve sampling, the `useFrame` camera math) into a `.mjs` script run from the project root (so `three` resolves from `node_modules`), construct a real `THREE.PerspectiveCamera` with the same params as the `<Canvas>`, and check actual NDC coordinates (`projectionMatrix * matrixWorldInverse`) for the thing in question. This correctly showed the summit's station labels project to valid on-screen NDC coordinates — ruling out a position/frustum bug — but NDC math alone can't prove a `Html` element actually paints in the live DOM (see lesson 28); it narrows the search, it doesn't close the case.
28. **A Node-script math simulation proving the intended math is correct is not the same claim as the live DOM/WebGL output matching it — conflating them here cost several redundant fix-and-report cycles.** The `distanceFactor` fix (lesson 26) was reported as resolving the summit's missing labels on the strength of NDC-coordinate math alone (lesson 27); the user's own follow-up screenshots (WebGL geometry rendering correctly, `Html` labels absent everywhere including the summit's own always-mounted, ungated one) proved that theory wrong on the very next round — scale couldn't be the cause of *total* absence, since even a small clamped-floor scale would still be visible, and it wasn't. The actual root cause was never found: this environment cannot render or inspect this project's live WebGL/Html output at all (canvas is permanently stuck at its default 300×150 size here — see dev-environment quirks above), so every claim about what the *live app* renders from this environment is unverified until confirmed against a real screenshot or the user's own testing. Two consequences for future work here: (1) don't report a 3D-rendering fix as resolving a visual bug without an actual screenshot confirming it — an NDC-math simulation is necessary but not sufficient; (2) if a `Html`/DOM-projected element in this scene is unreliable in a way that resists diagnosis, the pragmatic move — used for the summit's original "Checkpoints" panel in `Overlay.tsx` — is to route around the fragile 3D-projected mechanism entirely with a plain, camera-independent, fixed-position DOM overlay (the same pattern as the already-reliable quick-nav), rather than continuing to iterate blind on the thing that keeps not working.
    - **2026-07-22 update, part 1:** at the user's explicit request, the Checkpoints DOM panel was first replaced with `Html`-projected `StationLabel`s mounted at the top of each `Beacons.tsx` pillar — i.e. the exact mechanism this lesson says to avoid, reintroduced on purpose. The user's own screenshots confirmed it reproduced: no label at any beacon from the overlook, while the same `StationLabel` component worked fine elsewhere (ground level, moderate distance) in the same session.
    - **2026-07-22 update, part 2 — likely (not fully confirmed) root cause found:** tested `requestAnimationFrame` directly in this dev environment's Browser pane (`requestAnimationFrame(tick)` in a loop, timed against `performance.now()`) — it never fires; the call hung until tool timeout. This means R3F's entire `useFrame` render loop never runs here, which independently explains both this environment's permanently-300×150 canvas (never gets a resize/render tick) and *every* `Html` label being unmeasurable from here — it says nothing about whether `Html` itself is broken in the user's real browser, since a real browser's rAF does fire. Given that ambiguity plus the standing user report of *total* invisibility specifically from the overlook (not just "unverifiable from here"), the `Html`-based beacon labels were replaced with a from-scratch world→screen projection (`Vector3.project(camera)` in `Beacons.tsx`, written to `useUIStore().beaconLabels`) rendered as plain absolutely-positioned DOM buttons in `Overlay.tsx` — same DOM-overlay category of fix as the original Checkpoints panel, but tracking each beacon's live screen position instead of a static list. This still could not be visually confirmed from this environment for the same rAF reason; needs the user's real-browser testing to confirm it actually resolves the original symptom.
29. **`CylinderGeometry`'s end caps always fan out from the central axis point — a partial `thetaLength` slice does NOT give you a clean "circular segment" (flat chord + arc) shape, it gives you pie-slice caps that dip down to the axis center.** This is invisible in the one special case of an exact half-circle (`thetaLength:π`, where the axis center happens to already coincide with the chord line, so the "dip" is zero), which is exactly the case lesson 27-era work happened to use and ship without issue — but building the vault chest's lid with a *shallower* arc (a `thetaLength` well under π, to avoid a too-tall dome) directly this way produced a broken shape, confirmed via bounding-box output on the real installed `three` package (the naive on-paper chord/sagitta derivation predicted `y:[R-sagitta, R]`; the actual output was `y:[0, R]`, i.e. the pie-slice cap's center point pulled the bounding box all the way down to the old axis center regardless of the chosen angle window). The fix that actually works: build the *proven-correct full semicircle* first (clean caps, chord already at y=0), then apply a **non-uniform scale** to compress the height down to whatever shallow peak height is wanted — scaling can never un-flatten a cap or introduce a dip, it just changes how tall the dome reads — and only then rotate to reorient which axis is the chord vs. the extrusion. More generally: when a geometry needs reshaping in a way "resize an existing proven-good shape" and "rebuild from different constructor parameters" could both achieve, prefer the resize/transform — it inherits the older shape's already-verified correctness, while a fresh set of constructor parameters (like a different `thetaLength`) can silently land in an edge case the earlier verification never covered.
30. **When flipping a hinge/pivot to the opposite edge, both the pivot's position AND the child mesh's offset-from-pivot must mirror together — and the rotation's sign must be re-derived, not just carried over.** The chest lid's hinge was moved from the back edge to the front edge at the user's request (a 180° flip of which side it opens from). Tracing a fixed point on the lid's far edge through the rotation matrix for the new configuration showed the correct sign is the *opposite* of the original (`+angle` instead of `-angle`) — this doesn't fall out "for free" from flipping the position values alone, and asserting it without re-deriving would have very likely produced a lid that closes instead of opens, or opens into the ground, on the very next click.
31. **A decorative "proud shell" band positioned flush against the edge of the surface it wraps will z-fight if both it and the underlying surface have real end caps at that same edge — and giving it a cap to fix that reintroduces a second problem: `CylinderGeometry`'s cap is always a full disc fanned from the center, not a thin ring, so a uniformly-colored capped band paints almost the entire face that color.** This chest-dome "edge rail" saga took three passes to get right, each one fixing the previous fix's new symptom:
    1. Every band `openEnded:true` (no caps at all) — killed an initial z-fight (the edge rail's cap was exactly coplanar with the main dome's own cap, since both sit at the dome's true X extent — a classic "two flat surfaces on the identical plane" GPU-can't-decide flicker, not a lighting bug), but then the edge rails read as hollow/receded rather than flush, since a capless rail's outer boundary is just an open tube end with nothing behind it.
    2. Real caps back on the edge rails (`openEnded:false`) plus a small `EDGE_RAIL_MARGIN` (0.006 units) nudging their position so the cap plane is no longer exactly coincident with the dome's — fixed the z-fight *and* the hollow look, but every edge-rail mesh was still using one uniform black (`TRIM_DARK`) material across its whole surface. Since the cap is a full disc at nearly the dome's own radius (`ARCH_CHORD_R`, only slightly larger), that uniform black now painted almost the *entire visible side of the chest* black — the actual complaint that triggered this entry.
    3. The real fix: a **material array** for the edge rail geometry, same technique as the main dome (`domeMaterials`) — index 0 (the lateral surface, the only part that's actually meant to read as a "rail") stays `TRIM_DARK`, but indices 1/2 (the two flat caps) get `WOOD_SIDE`, the same tone as the dome's own side cap underneath. The cap is still geometrically present (so the piece still reads as solid/flush, and the margin still prevents any real z-fight), but now it's visually invisible — it blends into the wood instead of painting a black disc over it.

    General takeaway: when a "thin trim/rail" doesn't render as thin, check whether the *geometry* is actually thin (it usually is here — extrudeLength/ARCH_THICKNESS was never the problem) or whether a large incidental face (a cap, in this case) is being colored the same as the thin part it's attached to. A single uniform material hides that distinction completely; a multi-material array is what actually lets "this part should be trim-colored, this other part should just disappear into the background" coexist on one mesh.
32. **A flat 2D shape (`RingGeometry`, `PlaneGeometry`, etc.) and a real 3D volume are not interchangeable substitutes for "traces the same line from every angle" — a flat plane only has visible width from angles near its own face normal, and thins toward a hairline (eventually nothing) as the camera moves away from that normal.** The dome's rim strip (a thin border meant to trace the dome's semicircular side-cap edge, connecting with the side-frame border's real 3D boxes) was first built as a flat `RingGeometry` semicircle, positioned correctly (verified via bounding box, matching the dome's own footprint exactly) — but positioned *correctly* wasn't enough, because a flat ring's apparent on-screen width depends entirely on viewing angle, while the side-frame border's boxes keep a roughly constant apparent width from any reasonable viewing angle (they have real depth in the direction the ring doesn't). The two only lined up at the one viewing angle where the ring happened to face the camera; from anywhere else, the ring visually thinned out and a gap opened up against the border boxes, even though nothing about their *positions* had changed. Fixed by rebuilding the rim strip as a half-`TorusGeometry` (real tube volume in every direction) instead of a flat ring at the same position. General takeaway: if a decorative element needs to visually "connect" with a real 3D piece across a range of camera angles (not just one fixed shot), it needs to be genuinely 3D too — a flat plane's correctness only holds at the specific angle it was verified from.

    Making it a real volume wasn't the end of the story, though: the user still saw a gap afterward, because the rim strip's tube and its two neighbors (the outermost edge-rail band, and the side-frame border's front/back bars) were positioned *exactly tangent* — zero overlap margin, computed to touch at precisely one boundary plane each. Mathematically "touching" and visually "connected with no gap" are not the same thing once real-world rendering (anti-aliasing, shading falloff at grazing angles, minor floating-point slop) enters the picture — a seam with zero margin reads as a gap under most lighting/angles even when the two pieces are technically adjacent. The actual fix: introduce deliberate overlap (`RIM_TUBE_OVERLAP`, `SIDE_FRAME_TOP_OVERLAP`, both 0.02 units) so the rim strip's boundary sits *past* each neighbor's own boundary, not merely at it — computed directly off the neighboring piece's own known position (`edgeRailOuterX`), not as an independently-guessed offset, so the overlap can't drift out of sync if either piece's constants change later. General takeaway: when two decorative pieces are meant to read as continuous, don't position them to just meet — give them deliberate, generous overlap. "Touching" is a mathematical ideal that real-time rendering rarely honors visually.
33. **Every canvas-originated drag gesture needs its own `preventDefault`/`setPointerCapture`/touch-action hygiene (lessons 19/20) — including `CameraRig`'s own look-around drag, which had none.** Reported symptom: real station objects (chess piece, tokamak, piano, etc.) randomly replaced by their low-poly glowing-icosahedron `StationMarker` placeholder while looking up/down. Root cause: `StationsLayer` swaps a station's real component for its placeholder purely off `currentStationId` (`lib/hooks.ts`'s `useIsStationNear`), which is itself purely a function of scroll progress `t` (`nearestStation(t)` in `CameraRig`'s `useFrame`) — nothing else should be able to change it. But the look-around drag (pointer-drag to pitch/yaw the camera while parked) is a vertical/horizontal drag on the exact same canvas element `ScrollControls` treats as a scrollable surface, and its `onPointerDown` never called `e.preventDefault()` or `gl.domElement.setPointerCapture()`, and the canvas never had `touch-action: none`. A vertical look-around drag (looking up/down) is gesture-identical to a climb-scroll drag, so without capture it can leak into the underlying `ScrollControls` region and nudge `t` mid-drag — right at a station boundary, that's enough to flip `currentStationId` to a neighbor and unmount the real component. Fixed by giving `CameraRig`'s own drag the same treatment already used for in-station drags (e.g. `ChessStation`): `el.style.touchAction = "none"` once at effect setup, `e.preventDefault()` + `el.setPointerCapture(e.pointerId)` on `onPointerDown`, `el.releasePointerCapture(e.pointerId)` on `onPointerUp`. General takeaway: this lesson isn't automatically "learned" project-wide just because it's been applied once — audit *every* raw pointer-drag listener in the codebase against it individually, including ones (like the camera rig) that don't look like a typical "drag an object" interaction.
34. **A finite-difference tangent (`next - prev` between two nearby curve samples) is not a stable substitute for a curve's own analytic tangent when you then normalize it and cross it with another vector to get a width/side direction.** `PathRibbon.tsx` built each cross-section's left/right edge from `side = cross(tangent, up)`, where `tangent` came from subtracting two neighboring `PATH_SAMPLES` points and normalizing. On the steeper climbing stretches between stations (not at stations themselves, which sit on their own flattened pads — this is why the bug only showed up "during transitions") the path's horizontal (XZ) displacement between two adjacent samples can shrink close to zero even though the analytic curve is climbing perfectly smoothly. Normalizing a near-zero vector amplifies whatever floating-point direction noise is left in it, so `side` could swing wildly or flip sign from one sample to the next — pinching the ribbon to zero width and twisting the strip into a self-intersecting sliver, which read as a small dark shard (backlit by its own flipped face normal) floating on the slope. Fixed by using `PATH_CURVE.getTangentAt(t)` (the curve's real analytic derivative, which stays well-behaved) instead of a finite difference, with two safety nets since even an analytic tangent could in principle pass near-vertical: (1) reuse the last stable tangent direction if the current one's horizontal length is still near zero, and (2) force `side`'s sign to stay continuous with the previous sample (negate if `dot(side, prevSide) < 0`) so the ribbon's left/right edges can never swap between adjacent quads even if the tangent itself wobbles. General takeaway: prefer a curve's own analytic derivative over reconstructing one from nearby discrete samples whenever the result feeds into a normalize-then-cross-product — the discrete version has no guarantee against near-zero-length moments that the analytic one doesn't share, and normalizing amplifies that instability into a visible geometry defect that only appears at specific, hard-to-predict points along the curve.
35. **A module that mixes plain data with a heavy library dependency at module-load time will drag that whole library into anything that imports even just the data, however far downstream.** `path.ts` exported both pure `STATION_ORDER` data AND `PATH_CURVE` (a `THREE.CatmullRomCurve3`, built by executing `new THREE.CatmullRomCurve3(...)` at module scope, unconditionally, the moment the module loads). Three files that only ever wanted `STATION_ORDER` for plain metadata (`Overlay.tsx`'s nav labels, `StationPane.tsx`'s content lookup, `lib/hooks.ts`'s hash-sync) imported it from `path.ts` — and since all three are part of the page's always-eager tree (never behind a `next/dynamic` boundary), that one shared import statement pulled the entire `three` package into the first-load bundle, confirmed as a real ~680KB eagerly-fetched chunk in a production build's HTML output (`<script async>` tag present unconditionally). This had nothing to do with webpack chunk-splitting heuristics (see lesson 36 for that separate mechanism) — it's simpler and more direct: a module whose top-level code needs to run for any of its exports to be usable will run ALL of that top-level code, including the parts that build unrelated heavy objects, for every importer, even one that only destructures a single small plain-data export. Fixed by splitting the pure data into its own zero-dependency module (`stations-meta.ts`) and re-pointing the three eager consumers at it directly, while `path.ts` re-exports it too (so 3D-only call sites elsewhere didn't need to change). General takeaway: before adding a "just needs some plain data from over there" import to a component that's part of an always-eager tree, check what ELSE that source module does at load time — if it also constructs objects from a heavy library, that cost comes along for free and invisibly, regardless of how small the actual thing you imported is.
36. **`next/dynamic({ ssr: false })` prevents server-side rendering of a component — it does NOT guarantee the browser defers fetching its chunk.** Even after fixing lesson 35, a production build still hoisted `three`/`@react-three/*`/`@dimforge` (rapier's WASM loader) into a chunk with an unconditional `<script async>` tag in the initial HTML, verified the same way (inspect `npm run start`'s served HTML for `<script src>` tags, not the `next build` summary's "First Load JS" number — that number aggregates every chunk reachable from the page, sync or async, so it doesn't change when a chunk moves from eager to lazy or vice versa and can't be used to confirm this kind of fix). Root cause: these packages are imported from three separate `next/dynamic` boundaries (`WorldCanvas`, `TrailMapCanvas`, `VaultCanvas`), and Next's default webpack `splitChunks` cache groups (`framework`/`lib`/`commons`) use `chunks: "all"`, which considers a module's usage across BOTH sync and async import graphs when deciding whether to hoist it into a shared chunk — since three.js is "shared" by being used in 3 different async chunks, the default heuristic decided it was worth extracting into a chunk that then also gets attached to the main entry's eager script list. Fixed with a dedicated cache group in `next.config.mjs` scoped to `chunks: "async"` (`threeVendor`, matching `three|@react-three|@dimforge|three-stdlib` in `node_modules`), which keeps the extraction confined to chunks that are themselves only ever reached asynchronously. General takeaway: `next/dynamic(ssr:false)` controls SSR and the initial React tree, not chunk eagerness by itself — always verify against real served HTML when a "shouldn't this be lazy now?" bundle-size fix is made, since the build summary number can stay unchanged while the actual eager/lazy split is completely different underneath it.
37. **Mounting several heavy, independent things "as soon as possible after the reveal" just relocates the load-time hitch instead of removing it — and does so at the worst possible moment, right as the visitor starts interacting.** The first pass at deferred loading (lessons above) mounted `<Physics>` + all five interactive stations + all five decorative-environment pieces the instant `SceneReady` fired, in one React commit, and separately staggered the five stations' OWN mounting on a ~220ms-apart timer. Neither helped: the single-commit burst still did a large amount of synchronous work (WASM setup, geometry generation — see lesson 38) in one go, right after the page reveals — exactly when a visitor is most likely to start scrolling/panning for the first time — and `CameraRig`'s damping, while correctly delta-time-corrected (so it never permanently drifts), visibly **snaps** rather than smoothly catching up when a frame is delayed by a long synchronous block, since there's simply no frame rendered during the stall to interpolate through. The per-station timer made this worse in a different way: it turned a load-time problem into a mid-scroll one — a visitor scrolling quickly right after the reveal could reach a station before its staggered turn came up and watch it pop into existence. Fixed by (a) prefetching (plain `import()`, no mount) both deferred chunks the instant the parent mounts, decoupling "code downloaded" from "code executed," and (b) staging the actual mount across real `requestAnimationFrame` boundaries — not the same tick, and not an arbitrary `setTimeout` — so the browser gets genuine paint opportunities between each stage, and (c) dropping the per-station stagger entirely once (a) removed the network-burst problem it existed to solve, since it had no benefit left to justify its popping-in cost. General takeaway: "defer it until after first paint" is necessary but not sufficient — if the deferred work itself is heavy, it still needs to be spread across real frame boundaries, or it just moves the freeze from "before the user sees anything" (relatively harmless) to "right as the user starts interacting" (very noticeable).
38. **A `useMemo` that looks like "just compute some placements" can hide an accidentally-quadratic-feeling cost if the thing it calls internally does its own linear scan.** `Vegetation.tsx`'s `scatter()` does rejection sampling — up to `count * 14` candidate points per category — and each candidate calls `sampleTerrain()`, which itself does an O(239) linear scan over the path's samples (`nearestPathInfo`) plus a pad-blending loop. Multiplied out for high device tier (240 trees + 1100 grass + 90 rocks, before this fix), that's tens of thousands of `sampleTerrain()` calls in one synchronous `useMemo` — a genuine multi-hundred-millisecond block that landed squarely in the newly-deferred tier from lesson 37, undoing a good chunk of that fix's benefit on its own. Fixed two ways, deliberately kept separate: (1) split the three categories (rocks/trees/grass, cheapest first) onto their own staged animation frames, identical technique to lesson 37 but scoped inside this one component since it was the dominant single cost in the whole deferred tier; (2) trimmed grass instance counts (the most expensive category by far) as a direct, honest density-for-speed trade, while leaving `scatter()`/`buildInstancedMesh()`'s actual logic completely untouched — same seeds, same acceptance rules, so nothing about correctness changed, only cost and (for grass specifically) how many instances get placed. General takeaway: when hunting for a load-time hitch, don't just look at the top-level `useMemo`/`useEffect` that's slow — check what its own dependencies cost per call and how many times it's called; a "cheap-looking" helper called tens of thousands of times is where the real budget usually goes.
39. **Further code-splitting a `next/dynamic` boundary can shrink production bytes-over-the-wire without touching `next dev`'s cold-compile time at all — the two are bottlenecked by different things.** After splitting `WorldCanvas`'s decorative dressing into its own `DeferredEnvironment.tsx` chunk (on top of the existing `DeferredStations.tsx` split), the dev server's "Compiling /" time for a fresh process was measured before and after: ~9.3s both times, no meaningful change. Root cause: `next dev` (Turbopack or webpack alike) resolves and compiles the FULL reachable module graph for a requested route — including everything behind `next/dynamic` — as part of building its internal module manifest for that route, even though it doesn't SEND those chunks to the browser until the dynamic import actually fires at runtime. So the dev-mode compile cost is bound by the total number of distinct source files/packages touched by the whole graph (SWC transform throughput), which doesn't change just because those files get grouped into more or fewer chunks for delivery. This ISN'T wasted effort, though: the same split genuinely shrinks and better-sequences what a real (production) visitor's browser downloads/parses/executes, and — combined with lesson 37's frame-staging — determines what has to run in a single blocking burst once the deferred tier actually mounts. General takeaway: "First Load JS" / production bundle size and "`next dev`'s first-request compile time" are different metrics with different bottlenecks; a change that helps one can easily do nothing for the other, and testing only one of them after a splitting change can produce a misleadingly flat or misleadingly improved result for the metric you didn't check.

40. **Per-vertex `Math.random()` on a Gouraud-shaded mesh does not read as "fine grain" — it reads as blotches the size of each vertex's triangle fan, and it is almost always the real cause when terrain looks "splotchy".** The reported symptom was mottled, patchy-looking ground (worst on the snow and the dirt trail). Two lines were responsible, both of which *look* like reasonable texture-adding tricks: a `jitter = 0.9 + rand() * 0.2` per-vertex brightness multiplier applied to every vertex's final color, and a `if (rand() > 0.92) c.lerp(rock, 0.5)` "embedded pebbles" pass on trail vertices. The mistake in both is assuming vertex colors behave like a texture — they don't. A vertex color is INTERPOLATED ACROSS EVERY TRIANGLE TOUCHING THAT VERTEX, so an uncorrelated random value doesn't produce grain at pixel scale; it produces a smooth gradient blob spanning ~2 quads, and each neighbouring blob disagrees with its neighbours because their random draws are independent. That's precisely the "splotchy" appearance. It's worst on large flat-colored expanses (snow, packed dirt) where there's no lighting variation to hide it, which is exactly where it was reported. The `jitter` multiplier was also pushing colors out of gamut (measured max channel 1.033). **The fix is not less randomness, it's coherent randomness**: source variation from a smooth long-wavelength function of world position (`macroVariation(x,z)`, three sines at ~10–25 unit wavelengths) so adjacent vertices get near-identical values and the interpolation has nothing to smear, with the variation landing at a scale of many metres rather than one triangle. Measured over a real 191×191 high-tier grid, mean color difference between adjacent vertices dropped **5.5x** (0.106 → 0.019) while large-scale variation was preserved.

    The same rewrite fixed the second half of the complaint — that grass/rock/dirt didn't read as separate terrains — and the cause there was the opposite of what it looks like. It wasn't too little blending, it was too much of the WRONG kind: the old loop picked ONE material via a hard `if/else` chain (a stair-stepped boundary that follows the triangulation, and therefore changes shape with device tier, since tier picks the segment count) and then, in the grass branch only, smeared *up to 60% rock* across a wide 0.16-radian slope range on top of that. The result was a hard jagged line in some places and a huge zone of half-grass/half-rock that read as neither in others. The replacement applies materials as **ordered weighted layers over narrow `smoothBand()` transitions** — every boundary is smooth (no tier-dependent zigzag) but *short* (so each material dominates a well-defined area). Measured on the same grid, only 5.3% of vertices end up without a material above 75% weight. General takeaways, both worth remembering independently: (1) "smooth boundary" and "distinct materials" are not in tension — a narrow smooth band gives you both, while a hard threshold gives you a jagged boundary AND a wide ambient mix gives you mush; (2) a decorative detail that must vary per-vertex on an interpolated attribute needs a spatially coherent source, never a PRNG.

    Verification note: this environment can't render the scene (see quirks below), so the numbers above come from replaying the exact color loop over a real 191×191 grid in a Node script against the installed `three`, plus a top-down PNG render of the old and new vertex colors with lambert shading from the real normals. Per lessons 27/28 that is necessary but not sufficient — it proves the color data changed as intended, not that the lit 3D result looks right. Needs the user's own eyes in a real browser.

41. **A feature can be broken by two independent causes at once, and fixing the one you found first will look like it did nothing — `#station-<id>` deep links never worked, for two separate reasons.** Both had to be fixed together:
    1. **Reading a store value once on mount, when the thing that provides it mounts later.** `useStationHashSync` called `useUIStore.getState().requestScrollTo?.(t)` in a `[]`-dependency effect. But `requestScrollTo` is registered by `CameraRig`, which lives inside `WorldCanvas`, which is a `next/dynamic({ ssr: false })` import — so on a cold load it is reliably still `null` when that effect runs. The optional-chaining `?.` meant this failed *completely silently*: no error, no warning, just nothing happening. Fixed by subscribing to it (`useUIStore((s) => s.requestScrollTo)`) so the effect re-runs when the rig actually registers, however late. **General rule: `?.` on a store value that's populated asynchronously turns "not ready yet" into "silently dropped forever". If a call site can run before its dependency exists, subscribe — don't `getState()` once and shrug.**
    2. **A mirror/sync effect destroying the input before anything could read it.** The second effect wrote `currentStationId` back to the URL (`replaceState`) — and it runs on mount, when `currentStationId` is still its `"base"` default. So visiting `#station-chess` rewrote the URL to `#station-base` immediately, before the canvas chunk had even downloaded. Even a fully-fixed version of cause 1 would then have found nothing to restore. Fixed by capturing the incoming hash in a **lazy `useState` initialiser** (runs during the first client render, before any effect — and, unlike reading `window` during render unconditionally, it's SSR-safe because it doesn't run on the server) and gating the mirror effect until that captured value has been consumed.

    Verified in a real browser to the extent this environment allows: loading `/#station-chess` now leaves the hash intact after mount, where the old code replaced it. The other half — the handler registering late and the position then restoring — is **not** verifiable here, and for a sharper reason than previously documented: it's not just that `useFrame` never runs (lesson 28), it's that **R3F never commits the `<Canvas>` child tree at all in this environment**, confirmed by ScrollControls' scroll `<div>` being entirely absent from the DOM. So `CameraRig` never mounts, `setScrollHandler` is never called, and anything downstream of the rig existing is untestable from here by construction. Needs the user's real browser.

42. **An argmin/argmax over overlapping influence zones is not just "a bit rough at the seam" — it is a genuine DISCONTINUITY, and in a heightfield that means a vertical wall.** The terrain had this bug twice over, and both showed up as the reported "panels jutting out of the mountainside" and "corner turns are extremely discontinuous":
    1. **The reference height.** `sampleTerrain` raised the mountainside from `nearestPathInfo().y` — the height of the nearest point on the trail. That's an argmin, and the climb switchbacks: consecutive legs run ~10 units apart in XZ while sitting 5-10 units apart in ALTITUDE. Every point equidistant from two legs is a place where the winner flips and the reference height steps by the full difference between them, and those points form a line running the length of every switchback. Measured on a 400×400 grid over the real curve: **1,684 flip lines, worst step 10.24 world units across a single grid cell**, 338 of them inside the trail-blend zone where the term still carries most of the weight.
    2. **The station pads.** Lesson 1 replaced a sequential per-pad blend (which compounded into bulges) with a single max-weight winner. That fixed the bulges and introduced exactly the same class of bug one level down: where two pads' weights cross, the flatten TARGET snaps between two stations' anchor heights. After fixing (1), every single one of the worst remaining cliffs was within 1.3 units of a pad edge.

    For the path the answer is `smoothPathHeight()`: inverse-distance weighting (~1/d⁴) over decimated path nodes — no argmin anywhere — with `sampleTerrain` blending the exact nearest-point height into it over `REF_BLEND_END` just outside the corridor, so the trail bed still sits exactly on the real path while everything beyond ~3.7 units is smooth. That part worked and stands.

    **The pad half of this was fixed WRONG first, and the wrong fix was visibly worse than the bug — read the rest of this entry before touching `PADS`.** The first attempt kept the flatten STRENGTH as the plain maximum but made the flatten TARGET a normalized weighted average (4th-power falloff), on the reasoning that a neighbour would contribute under 1% at a pad's own rim. That reasoning silently assumed the flatten discs don't overlap. **They did**: measured against the real anchors, `base`/`intro` overlapped by 0.03 units and `intro`/`chess` by 0.27, and even outside the overlap the blend zones are so much wider than the spacing that at chess's own visual rim the neighbouring `intro` pad carries weight 0.9525 — 0.9525⁴ = 0.823, nowhere near "under 1%". Result: the ground rose **1.6 units in the middle of chess's platform**. `StationPad` renders a cylinder whose underside clears the flattened ground by **0.01 units**, so that is 160x the tolerance — plates of terrain erupting straight through the station bases, reported as the terrain looking "scaffolded" with "interfering/intersecting planes." Two general lessons, both worth more than the specific fix:
    - **When a station platform's clearance over the terrain is 0.01 units, "approximately flat" is not flat.** Any pad change must be checked against exact flatness inside every VISUAL pad radius, not judged by a smoothness average.
    - **Two overlapping flatten discs are an unsatisfiable constraint, not a blending problem.** Each demands the ground be flat at a different height; no weighting scheme resolves that. Fix the geometry.

    The actual fix is both: `PAD_RADII` gives each station its own flatten radius sized so no two discs overlap (base 2.6→2.4, intro 2.6→2.2, chess 2.6→2.4, all still exceeding their visual radii), and the flatten target is **exclusive inside a disc** — that pad's own height and nothing else's, which the non-overlap guarantee makes unambiguous — falling back to the smooth weighted average only OUTSIDE every disc, where there is no flatness to preserve and a smooth pad-to-pad crossover is what avoids the original step.

    Separately and in the same pass: `Math.max(d - TRAIL_HALF_WIDTH, 0)` and `Math.min(..., cap)` are continuous but have hard kinks in their DERIVATIVE, and a derivative kink in a heightfield is a visible crease — here, fold lines running the entire length of the trail at a constant distance from it, and along the roughness cap's own contour. Replaced with `softRamp`/`softCap`, C1 versions rounded over a small width.

    **How to measure this, because the first pass measured it wrong and shipped a regression.** Averaging smoothness over the whole terrain is misleading: most of the surface is distant flank that barely appears on screen, and a big improvement there can mask a regression in the narrow band the camera actually flies through. Always restrict to the **near-trail band** (within ~12 units of the path) and always check **pad flatness** separately. `scratchpad/terrain-audit.mjs` (rebuild it if gone — it replays the height function for several variants side by side) reports, for the near-trail band only: max single-cell step, mean/max crease (second difference), high-frequency energy (deviation from a 3×3 mean, which catches ripple a second difference under-weights), and worst deviation from the exact target height inside every visual pad radius.

    Final measured result, near-trail band, versus the ORIGINAL pre-change terrain: **max step 0.48x, mean crease 0.30x, max crease 0.47x, high-frequency energy 0.31x, and pad deviation exactly 0.0000** (the original also achieved 0 here; the intermediate broken version hit 1.6). A shaded-relief render makes the path half obvious — the old surface is covered in a fan of hard crease lines radiating from the trail, essentially all of which are gone. Cost: `smoothPathHeight` measures 5.6ms per 40,000 samples (~11ms across the whole world build), so it does not give back lesson 35's chunk-pruning win; node stride 6 and stride 1 measured identical on every metric, so the cheap stride is kept.

    **What is NOT fixable by terrain math, if this comes up again:** the remaining worst crease sits at the `tokamak`/`vault` rim, where the two anchors are 5.94 units apart in XZ but **8.24 units apart in altitude**; `intro`/`chess` is similar (4.93 apart, 3.55 of altitude). The ground between them has to climb that much over roughly a unit of gap — that is a design constraint of where the stations sit, not a blending artifact, and no weighting scheme makes it gentle. The lever is `stations-meta.ts` (`t` spacing / lateral `distance`), i.e. moving the stations apart — a content decision, not a math one.

43. **drei's `ScrollControls` ignores every scroll event during its own first animation frame, and `state.offset` is only ever written from inside that handler — so a programmatic `el.scrollTop` write landing in that window is silently lost.** From its source (`node_modules/@react-three/drei/web/ScrollControls.js`): it sets `el.scrollTop = 1` on mount to allow upward scrolling, then guards `onScroll` with `let firstRun = true; ... if (!enabled || firstRun) return;` and clears the flag in a `requestAnimationFrame`. `useFrame` damps `state.offset` toward `scroll.current`, which nothing but `onScroll` assigns. Consequence for `#station-<id>` deep links: the DOM scroll position was set correctly and the camera never moved, because ScrollControls never learned about it — and then the first real user scroll read the already-offset `scrollTop` and jumped, which is exactly the reported "it doesn't go back at first, then starts scrolling from that position onward". Note the listener only attaches once `events.connected === el`, itself deferred by a `requestAnimationFrame`, so the dead window is at least two frames after mount. Fixed by deferring the deep-link restore to `sceneReady` (many frames later) and using the ANIMATED travel rather than a single write — a tween writes `scrollTop` on every frame for a second or more, so it cannot be lost to one mistimed event. General rule: **anything that programmatically drives ScrollControls must run well after mount, and preferably write more than once.**
44. **A module reached BOTH statically and via `import()` can be instantiated twice, and then "shared" module state silently isn't — this cost two failed fixes before it was found.** `useAudioPrewarm` reached `lib/tonePlayer` through `import("@/lib/tonePlayer")` while `PianoStation` imported it statically. A running dev build showed **two distinct `lib_tonePlayer_ts_*` chunks and two distinct `node_modules_tone_build_esm_index_*` chunks**. With two module instances, prewarm builds the synth in one copy while the piano reads `synth === null` from the other, so every first note pays the full cold cost no matter how correct the prewarming logic is. Two defences, both applied: the hook now imports the module **statically** (safe — `tonePlayer` imports nothing heavy at module scope, `tone` stays behind a dynamic import inside it; verified against the production build's served HTML that no tone/three/rapier chunk is eagerly `<script src>`-tagged), and the module's state lives on **`globalThis`** so a duplicated evaluation still shares one synth. **Whenever module-level state must be a true singleton, put it on `globalThis` — bundler chunking is not a guarantee of single evaluation.** Diagnosing this needed a real browser: `globalThis.__portfolioTonePlayerState` is deliberately inspectable, so `{toneLoaded, synthBuilt}` can be read from the console after a gesture.

    Also fixed here: the unlock must run **synchronously inside the gesture**. The hook's old `import(...).then((m) => m.prewarmSynth())` put a dynamic import — and on a cold load a network fetch of Tone — between the gesture and `Tone.start()`. Chrome's sticky activation forgives that; Safari's transient activation does not. `preloadTone()` now runs on mount (a download needs no gesture) so the module is in hand, and `prewarmSynth()` is synchronous. The hook also keeps listening across gestures until `isAudioReady()`, since the first gesture can land before Tone finishes downloading.

    Measured in a real browser, this Tone version: cold path = 7.7ms PolySynth construction + **21.1ms voice allocation** + 3.7ms trigger, plus Tone's default 100ms lookahead. Warm path after one gesture = **3.4ms**, `contextState: "running"`, `lookAhead: 0.02`.
45. **`Tone.PolySynth` cannot be pre-warmed — it garbage-collects its own voices, so a warmup is silently undone while the page sits idle. Do not use it for an instrument the visitor triggers by hand; use a permanently-held pool of plain `Synth` voices.** This was the real cause of "the first note is delayed and interferes with the second", and it survived THREE earlier fixes because each one was verified by triggering a note immediately after warmup — which passes. Measured against Tone 15.1.22 in a real browser, voice count after a silent 4-note warmup: **4 at +5s, 4 at +10s, 3 at +15s, 3 at +25s, 2 at +30s and still falling**; `new PolySynth(...)` itself creates ZERO voices (allocation is lazy, ~21ms for four). A visitor scrolls far longer than 30s before reaching the piano, so the warmup is fully reclaimed by the time it matters and the first press pays full allocation. Replaced with `VOICE_COUNT` plain `Synth` instances built once, referenced forever, round-robined per note. Verified with the same idle test: **12/12 voices alive at every checkpoint through 30s, first note after 30s idle 3.6ms vs 3.0/1.8ms for the next two** — i.e. the first note is no longer distinguishable from the rest (PolySynth gave 5.8ms vs 2.0ms with voices only partly reclaimed).

    Two supporting fixes, both also required: (a) `playNote` was `async` and awaited before triggering, so even a warm synth scheduled the note a microtask or more after the click and two presses could resolve almost simultaneously regardless of their real spacing — there is now a fully synchronous fast path; (b) **Tone's default `lookAhead` is 0.1s**, right for sequenced playback and a flat 100ms of latency for an instrument someone is clicking — lowered to 0.02 (lowered, not zeroed: too low risks dropouts).

    **Method note, which is the transferable part:** a warmup/caching optimisation must be verified *after a realistic idle delay*, not immediately after warming. Testing it immediately measures the one case where it always works and hides any reclamation, eviction or expiry the runtime does in between.
46. **"Make the colours more separable" is measurable, and eyeballing hex values is not the way to do it.** Classify every terrain vertex by its dominant material, average the colour ACTUALLY produced for each class (after all the layer blending and variation, not the raw palette constant), convert to Lab, and report pairwise CIE76 dE — the number that matters is the MINIMUM pair, i.e. the two terrain types most likely to be confused. Doing that here immediately showed the real problem was not the one that looked obvious: the worst pair was **rock/pad at dE 16.6** (both grays), not grass/rock. The fix follows from that: push materials apart in LIGHTNESS as well as hue, because two colours differing only in hue collapse into each other under shading — rock cooler and darker, dirt warmer and more saturated, snow brighter, pad stone lighter and more neutral so it reads as cut stone rather than more rock, plus a lower `BIOME_STRENGTH` since a strong per-station tint works directly against grass reading as grass. Result: worst pair 16.6 → 24.4 dE (1.47x), every other pair improved too. Re-measure with the same method before retuning.

47. **The canvas is NOT what receives pointer input in this app — ScrollControls' own `<div>` is — and three separate bugs all traced back to not knowing that.** Read `node_modules/@react-three/drei/web/ScrollControls.js` and `@react-three/fiber`'s `DOM_EVENTS`/`createPointerEvents` before writing any pointer handler here. The two facts that matter:
    - ScrollControls creates a `<div>`, appends it to **`gl.domElement.parentNode`** (a sibling that fully covers the canvas), makes it the page's real scroll container, and then calls **`events.connect(el)`** — re-pointing R3F's entire event system at that div. So the canvas receives nothing, and `touch-action` set on the canvas governs nothing.
    - R3F registers its own `pointerdown` listener as **`{ passive: true }`** (`onPointerDown: ['pointerdown', true]`). `e.nativeEvent.preventDefault()` inside a mesh's `onPointerDown` is therefore ignored by the browser and only logs "Unable to preventDefault inside passive event listener invocation."

    The three consequences, all real bugs that were live simultaneously:
    1. **`CameraRig`'s look-around drag, ctrl+wheel zoom and pinch zoom never fire at all** — every one of those listeners is on `gl.domElement`. They are inert today; the on-screen hints for them were removed rather than left advertising nothing, and the code is kept (with a note in the file) so it can be re-pointed at the real event element deliberately. **Do not trust CLAUDE.md's older claims that look-around "works" — none of them were ever verified in a real browser** (lesson 28 warned about exactly this).
    2. **A touch that starts on a 3D object still starts a native scroll of that div**, because the finger went down inside a scrollable element. Invisible on desktop (a mouse drag scrolls nothing); on touch it means dragging the chess piece or the tokamak also flies the camera up the mountain. That is the whole "tap/hold is glitching and fighting the camera, works fine on desktop" report — and note the two earlier rounds of feel-constant tuning could never have fixed it. The fix has to suppress the scroll where it can actually take effect: capture-phase, non-passive `touchstart`/`touchmove` `preventDefault()` gated on a live object gesture (`lib/dragState.ts`). This works because **touch input dispatches `pointerdown` BEFORE `touchstart`**, so the object has already claimed the gesture by the time the blocker runs.
    3. **Once the browser reinterprets the gesture as a scroll it fires `pointercancel`, and nothing listened for it.** A drag that only ends on `pointerup` then stays latched "in progress" forever: the object keeps following every later pointer move anywhere on the page, and the now-retired pointerId goes on to throw a `DOMException` out of `releasePointerCapture` on the next tap — an uncaught throw from a window listener, which is what surfaced as **error overlays on screen**. Every drag must handle `pointercancel`, and `set/releasePointerCapture` must be guarded (`hasPointerCapture` + try/catch): on touch a pointerId stops being "active" the moment the finger lifts, so those calls throw as a matter of routine, not as an edge case.

    General takeaway beyond this codebase: when a library "connects" or "attaches" its event system, find out to WHICH element, and check the listener options. A handler that looks correct can be attached to an element that never sees the event, and `preventDefault()` can be silently discarded — neither failure produces an error, so both survive several rounds of plausible-looking fixes aimed at the wrong layer.
